# Beacon Grafana dashboards

The "Beacon Chain" Grafana dashboards for the mainnet followers, generated by the
scripts here. Grafana on ethlambda-4 file-provisions them from
`~/metrics-beacon/dashboards/` (read-only, reloaded within 30 s), so a change is
made here, generated, and copied there; an edit in Grafana's UI does not stick.

| Dashboard (uid) | Generated by | Reads |
|---|---|---|
| Beacon Follower (`beacon-follower`) | `gen-dashboards.py` | Prometheus, and the nodes' `block_events` rows in ClickHouse |
| Ethrex L1 (`ethrex-l1`) | `gen-dashboards.py`, from `ethrex_dashboard.upstream.json` | Prometheus |
| Beacon client comparison (`client-compare`) | `gen-compare-dashboard.py` | ClickHouse: ethlambda, Lighthouse and Silver rows |
| ethlambda A/B (`ethlambda-ab`) | `gen-ethlambda-ab.py` (imports `gen-dashboards.py`'s SQL) | Prometheus and ClickHouse, two nodes side by side |
| Silver + ethrex (eth-5) (`silver-eth5`) | `gen-silver-dashboard.py` | Silver's own ClickHouse |
| Actor runtime (spawned) (`spawned-actors`) | `gen-spawned-dashboard.py` | Prometheus, `spawned_*` series |

## Generating

From this directory, Python 3 with the standard library only:

```bash
python3 gen-dashboards.py dashboards/beacon-follower.json ethrex_dashboard.upstream.json dashboards
python3 gen-compare-dashboard.py dashboards/client-compare.json
python3 gen-ethlambda-ab.py dashboards/ethlambda-ab.json
python3 gen-silver-dashboard.py dashboards/silver-eth5.json
python3 gen-spawned-dashboard.py dashboards/spawned-actors.json
```

then copy `dashboards/*.json` to ethlambda-4's `~/metrics-beacon/dashboards/`.

`gen-dashboards.py` rewrites the Beacon Follower in place. It owns only some of
its rows (`beacon_rows()`: Gossip validation through Per-block processing
(ClickHouse)), dropping and rebuilding those, and carries every other row
through from its input untouched. Overview, Fork choice, Peers and Block import,
whose ClickHouse panels include the epoch-start import cost, are therefore
maintained in `dashboards/beacon-follower.json` itself. That file is what is
deployed; the first regeneration renumbers some panel ids, and a second changes
nothing. The other dashboards are built whole by their script, so only the
Beacon Follower's JSON is kept here.

## Stage names

ethlambda renamed its `block_events` stages to `<section>_start` and
`<section>_end` (lambdaclass/ethlambda#917; see `docs/telemetry.md`). Rows
written before keep the old names, and Silver's rows always carry them.
`stage_names.py` holds the mapping, and every generator passes its finished
dashboard through `stage_names.apply`, which turns each `stage = 'received'` in a
query on ethlambda's ClickHouse into `stage IN ('received', 'import_start')`.
Write new SQL with the old names; the pass adds the new ones. Queries on Silver's
own ClickHouse are left alone. `python3 stage_names.py <dashboard.json>...`
applies it to a dashboard file in place.
