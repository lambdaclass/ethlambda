ethlambda

Command line

ethlambda follows one of two chains, selected by a subcommand:

InvocationChain
ethlambda node <flags>The lean consensus protocol this repository implements
ethlambda beacon <flags>The Ethereum Beacon Chain, as a gossip follower
ethlambda <flags>node: the subcommand is injected

Four subcommands follow no chain. ethlambda replay-era replays real chain history from .era files and checks it against the states stored in them; see era_replay.md for its flags and checks. ethlambda benchmark is the offline benchmarking harness, covering block building (benchmark synthetic, run through make bench) and block import (benchmark import fetch / benchmark import replay). See benchmarking.md for what each workload measures; benchmark import’s flags are in their own section below. ethlambda validator is the validator client: a separate process that holds keys and performs duties against a beacon node over the standard REST API, documented in its own section below. ethlambda voluntary-exit signs one validator’s voluntary exit and hands it to a beacon node; see its section below. ethlambda slashing-protection moves that client’s EIP-3076 history in and out of its directory, offline; see its section below.

node is the default

clap has no native default subcommand, so the binary rewrites its own argv before parsing. If the first argument is not node, beacon, benchmark, replay-era, validator, help, -h, --help, -V, or --version, then node is inserted ahead of it. The function is inject_default_subcommand in bin/ethlambda/src/command.rs. Every subcommand has to be listed there: a missing one would have node inserted ahead of it and become unreachable.

ethlambda --genesis c.yaml ...              ->  ethlambda node --genesis c.yaml ...
ethlambda node --genesis c.yaml ...         ->  unchanged
ethlambda beacon --gossipsub-port 9001 ...  ->  unchanged
ethlambda benchmark synthetic ...           ->  unchanged
ethlambda --help | --version | -h | -V      ->  unchanged, no injection

This is what keeps every existing caller working with no edit: the Docker ENTRYPOINT, lean-quickstart’s client-cmds/ethlambda-cmd.sh, the Hive lean client shim, preview-config.nix, and the docker run blocks in the devnet-runner skill all pass bare flags.

ethlambda with no arguments at all is left alone, so it prints the subcommand listing rather than a missing-flag error for node.

Accepted range is CUSTODY_REQUIREMENT to NUMBER_OF_CUSTODY_GROUPS (4 to 128), enforced at parse time rather than clamped: serving a different set than the operator asked for is the failure hardest to notice.

It is not the number of columns custodied. That is sampling_size, the larger of this and SAMPLES_PER_SLOT, so the default still custodies 8 columns and the two only converge once the flag is raised past 8. A node at 128 is a supernode, custodying every column; raising the value costs storage and bandwidth in proportion and makes this node useful to more peers, which on a network where a cgc=4 peer holds 4 of 128 columns is what decides whether a lookup finds a custodian at all.

Changing it changes which columns this node custodies, since the custody set is a function of the node id and the count. Sidecars already on disk belong to the old set: nothing is corrupted, but the node advertises a set it has not finished filling until it backfills the difference.

With neither execution flag, the follower contacts no execution client and imports blocks without validating their payloads, which is what it did before those flags existed. It then answers attestation_data, aggregate_attestation and block production with 503, so a validator client cannot use it. Supplying one without the other is refused at startup: an Engine API endpoint always requires authentication. See the execution layer pairing for what each verdict does and for the limitations that go with the retry ladder.

The genesis constants are checked twice at runtime: checkpoint sync verifies the downloaded anchor state against both, and a resumed data directory is checked the same way, so a wrong constant fails at startup rather than following the wrong chain.

beacon therefore takes no genesis config, validator registry, or bootnode file of its own the way node does: those are read off the resolved network instead of being separate operator input, and beacon’s --bootnodes only adds entries to the network’s list (see Bootnodes on beacon). A config.yaml (a directory’s, or a built-in network’s embedded one) is read permissively: absent keys fall back to mainnet’s values, numbers are accepted quoted or bare, and unrecognised keys (on a current config, the heze schedule this build does not claim) are dropped with one warning line naming each. Its PRESET_BASE (mainnet or minimal) selects the preset the process runs, before anything is decoded against it; a missing or unknown one is a hard startup error. The validator client has no --network and adopts the preset its beacon node’s /eth/v1/config/spec reports. Sepolia’s config schedules gloas, which this build follows, so it parses and runs like any other fork. A scheduled fork the build claims but does not follow gets a separate, explicit warning at startup, since the chain follower would stop tracking the chain there regardless of what parsed cleanly; none exists today. The keys this build runs on compile-time constants for (the custody and subnet counts, the MAX_REQUEST_* limits, MAX_PAYLOAD_SIZE, the snappy message domains and MAXIMUM_GOSSIP_CLOCK_DISPARITY) must equal those constants, or startup fails naming each key that differs: the node cannot follow a network that sets them otherwise, and /eth/v1/config/spec would report values it does not use. For a directory, both checks run before its genesis.ssz is decoded, so a directory built for the other preset fails with the preset error rather than an SSZ one.

Resuming a data directory under a config.yaml whose CONFIG_NAME differs from the stored one only logs a warning; the stored name is kept. Any changed chain value (a fork epoch or version, the slot time, PRESET_BASE) is still a hard error.

--checkpoint-sync-url now supplies the beacon anchor: a finalized BeaconState and its anchor block, fetched from a standard Beacon API server and verified against the genesis identity above plus the anchor’s own internal consistency (see checkpoint_sync.md). The full anchor precedence is: a resumable data directory, then --checkpoint-sync-url, then, for a loaded network only, that directory’s own genesis.ssz, then abort. The URL is therefore required on a fresh data directory only for a built-in network: no built-in network carries a genesis state, and anchoring one at genesis would leave the follower replaying a chain that has been live for years. A loaded network’s own genesis state is a legitimate anchor instead, since a freshly started devnet has no checkpoint provider at slot 0 and this is the only way to join one. A directory already anchored from a previous run resumes without the flag either way, the same way node’s does.

--api-port is bound here too, off beacon’s own anchored store: one HTTP call site serves both chains, but it picks the router by the store’s chain, so a beacon run serves the Beacon API under /eth/v1 and /eth/v2 and answers a /lean/v0/... path with a 404. See rpc.md.

Bootnodes on beacon

beacon’s --bootnodes is a list, not a file, modeled on Lighthouse’s --boot-nodes. Entries are comma-separated and the flag may be repeated, all of its values combined; each entry is trimmed, and an empty one is ignored. An entry is either an ENR, written with or without its enr: prefix, or a multiaddr, which starts with /:

ethlambda beacon --network hoodi --checkpoint-sync-url <URL> \
  --bootnodes enr:-Iq4Q…,/ip4/203.0.113.7/tcp/9000/p2p/16Uiu2HAm… \
  --bootnodes /ip4/203.0.113.8/udp/9000/p2p/16Uiu2HAk…

A multiaddr is /ip4/<ip> or /ip6/<ip>, then one transport, then /p2p/<peer-id>. The transport decides what the entry is used for:

TransportThe peer is
tcp/<port>dialed over TCP
udp/<port>/quic-v1dialed over QUIC
udp/<port>not dialed directly: the port is the peer’s discv5 port, so the entry seeds discovery, which is how Lighthouse reads a UDP multiaddr too

QUIC is quic-v1 only; the older draft /quic is refused. The /p2p/<peer-id> is required, and DNS multiaddrs (/dns, /dns4, /dns6, /dnsaddr) are refused, so write the address as /ip4 or /ip6. Those two are departures from Lighthouse; Peer discovery lists them with the rest.

The entries are added to the resolved network’s own list (a built-in network’s embedded one, or a loaded directory’s bootstrap_nodes.yaml/.txt), never put in its place, which is Lighthouse’s behavior too. Giving the flag used to replace that list; now the network’s bootnodes are always used, and the flag only adds to them. Nothing turns them off: each one with a QUIC or TCP port is dialed at startup and redialed 12 seconds after every failed dial or disconnect, even on a host that cannot reach it. To run on other bootnodes alone, load the network from a directory whose bootstrap_nodes.yaml lists only those.

An IPv6 entry is dialed like an IPv4 one, but discv5 binds the IPv4 wildcard and an IPv4 socket cannot reach an IPv6 address, so an IPv6 entry that is only a discv5 contact (/ip6/<ip>/udp/<port>, or an ENR whose only address is ip6 and whose only port is udp) is refused. The check reads the address discovery binds rather than assuming IPv4, so it lifts on its own once discovery binds IPv6 (#853).

Every entry is checked at startup. One that does not parse, or that is unusable (an ENR with no quic, tcp or udp port, a port of 0, and so on), is a startup error naming the entry: an operator who typed it meant to reach that peer, and skipping it would leave the node running on a list it was not given. The network’s own list keeps the old rule, a bad entry there being skipped with a warning, as node skips one in its file.

A file path is no longer accepted. Startup fails on one, with a hint that --bootnodes now takes a list; so does a missing path ending in .yaml, .yml or .txt. A launch script that passed beacon a bootnode file must pass the records it lists joined with commas instead (without a YAML list’s - markers or any comments), or, for a network loaded from a directory, list them in that directory’s bootstrap_nodes.yaml.

What ethlambda beacon does today

It follows the resolved network as a non-validating follower. It anchors a RocksDB-backed store at a checkpoint-synced (or resumed) finalized state, joins the network’s gossip and req/resp, and the chain actor imports blocks from there (phase0 through gloas), runs fork choice, and, with --execution-endpoint, asks an execution client about payloads. It never proposes or attests. See beacon_wire.md for what goes on the wire and how to check a run against the live network.

validator flags

ethlambda validator is not a node. It binds no libp2p port, opens no chain database, runs no discovery and follows no chain: it holds validator keys and performs duties against a beacon node’s standard REST API. It works against any conformant beacon node, this repository’s beacon subcommand or another implementation’s, so none of the common flags apply to it.

Slashing protection lives in --validators-dir/slashing_protection.json, locked to one process, so --validators-dir must be writable: a read-only mount of the keys (a Kubernetes Secret, a :ro volume) fails at startup, as does a record that is a symlink (say, onto another volume) rather than a regular file, since a dangling one would read as “no record”; and the directory should be a local disk, since every signature waits for the record to be flushed to it, and the lock that keeps a second process off it is an flock, which a network filesystem may not honour. Unix only. Run the client under a supervisor that restarts it (systemd’s Restart=on-failure, a Kubernetes pod): if a bug ever panics while the record is held, the record is unusable for the rest of that process and no attestation or block can be signed, so the client stops at once and exits with a failure, after letting a keymanager request in flight finish, and the restart rereads the record from disk. A key with no record is refused at startup unless --init-slashing-protection is passed. A key moving here from another client brings its history with slashing-protection import, or in the same keymanager API request that imports the key. See Spec Deviations.

What it does today

Attestations, block proposals and attestation aggregation, and from gloas on the self-built payload envelope and the payload timeliness committee vote.

Each epoch it resolves its validators’ indices, fetches their attester duties for this epoch and the next, fetches this epoch’s proposer duties, subscribes to the committee subnets the attester duties need, and registers each validator’s fee recipient with the beacon node. The subscription also tells the node which committees this client will aggregate for, which it has to know in advance so it can collect the votes.

With --builder-proposals, before gloas, it also signs a builder registration (fee recipient and gas limit) for each validator the node resolved and sends them to every node: the full set after each epoch’s refresh, in batches, and every slot only the registrations whose fee recipient or gas limit changed through the keymanager API. A block request then carries a builder_boost_factor, and when the node answers with a blinded block it is signed like a full one and published to blinded_blocks on the node that produced it, with no failover. A publish that node does not confirm is logged at error and counted as unconfirmed, not as a missed proposal, since the relay may still publish the block.

From the epoch before gloas on, it also signs a proposer preferences message (fee recipient and target gas limit) for each of its proposal slots in the current and next gloas epoch, and sends them to every node. This happens every slot, whether or not --builder-proposals is set: from gloas the preferences are what carry a proposal’s fee recipient, and a node ignores builders’ bids for a slot with none. It reads those duties from the v2 proposer duties endpoint, whose dependent root the preferences must carry, and publishes each (slot, dependent root) until every node has accepted it, sending the message as first signed to all of them again each slot until then, and again after a reorg changes the root. After that it sends each one, as first signed, once more every epoch while its slot is ahead, at the epoch’s second-to-last slot (or the next poll after it, if a slow node made the client skip that one), since a node that restarts loses what it accepted. A node restarted mid-epoch thus lacks the preferences of the slots before that re-send and holds the later ones; one restarted after it lacks the next epoch’s too, all but its last slot’s, which the next epoch’s re-send covers. A re-send covers only the slots that have not started when its duties fetch returns, so slow nodes ahead of the one that answers can leave the next epoch’s first slots out. Each preference is its own request, and a poll sends all of them, for both epochs, to every node at once, so a node that does not answer delays the end of the poll by one request timeout, not the other nodes’ delivery. The duties are fetched from one node at a time, so each node that does not answer, listed ahead of the one that does, delays every send by a request timeout. Duties outside their epoch, and all but the first for a slot, are dropped before anything is signed. A validator with no fee recipient is skipped, with one warning per epoch naming the count. A preference cannot be replaced for the same slot and root, so a fee recipient changed through the keymanager API applies from the next dependent root.

Each slot it wakes at the boundary. If one of its validators proposes that slot, it signs the RANDAO reveal, asks the beacon node for a block, checks that the block is for the slot and proposer it asked about, signs it and publishes it. One third into the slot it fetches the attestation data, checks that it is for the slot it asked about and that its index is one the slot’s fork allows (0 before gloas, 0 or 1 from it, where it is the payload signal), signs for every validator due that slot, and submits the batch. A node whose answer fails either check is passed over for the next one in --beacon-nodes, before anything is recorded or signed. Two thirds in, for any duty it was selected to aggregate, it asks the node for the aggregate covering that committee’s votes on the data it just signed, wraps it with the selection proof and publishes it.

Aggregation is not a choice. A validator signs the slot under a dedicated domain, and whether the hash of that signature divides evenly by a modulus from the committee’s size decides it. Signatures are deterministic, so a validator gets one answer per slot, cannot search for a better one, and cannot decline: the beacon node checks the same thing when the aggregate arrives.

Proposals are bounded by that one-third mark rather than by the end of the slot. The specification defines no block-production deadline; the nearest thing it defines is the point attesters stop waiting for a block, which is the same instant. A proposal still running then has already lost most of the block’s value, and every second past it comes out of this client’s own attestations, so it is abandoned and the slot’s attesters still vote. A blinded block that was already signed is the exception: its publish runs on its own task, since the beacon node may wait several seconds on the relay, so an overrun after signing is logged at info and not counted as a failed proposal, and the task counts the real outcome (a refusal as a failed proposal, success with its publication delay).

Electra is the earliest fork it will propose under. A deneb block body has one field fewer than an electra one, so it would need a container pair of its own, and it would buy nothing: the attestations this client submits are electra’s SingleAttestation, which has no earlier form, so a pre-electra chain is one it cannot serve whatever it does with blocks. A block from any earlier fork is refused by name rather than failing to decode.

Blocks are fetched and published as SSZ rather than JSON. Signing a block means computing its hash_tree_root, which only the typed container can give; a hand-written JSON mapping of an execution payload would be a large surface on which a single wrong field silently produces a signature over the wrong block.

From gloas on a proposal is two messages. The client asks for the block with include_payload=true (produceBlockV4), publishes the block bare, then signs the envelope with the proposer’s own key under the builder domain and publishes it with its blobs and cell proofs (Eth-Blob-Data-Included: true). Both go out as SSZ. The envelope shares the proposal’s budget (the attester offset, below), so a proposal that overruns it is abandoned wherever it is. A failure to publish the envelope is logged at error and counted, and does not fail the proposal. A block that commits to a builder’s bid is left alone.

Each epoch it also fetches the payload timeliness committee duties for the validators it holds, for this epoch and the next when they are gloas ones. The gloas fork epoch’s are the exception: a node cannot know them before the fork, so they are fetched at the fork epoch’s first slot rather than as the previous epoch’s lookahead. When an epoch’s schedule could not be fetched, the client asks again after each slot’s duties until it has one. A member sleeps until PAYLOAD_ATTESTATION_DUE_BPS of the slot, asks the node for the payload attestation data, signs it under the PTC domain and submits it. A 204 (the node knows no block for the slot) means no vote. So a gloas slot runs in this order: propose at the boundary, attest at ATTESTATION_DUE_BPS_GLOAS, aggregate at AGGREGATE_DUE_BPS_GLOAS, then the committee vote. The attestation and the committee vote are each bounded by the end of the slot.

Sync committee duties run beside the attester and committee work, not after it. Each epoch the client fetches its sync duties for the current period and the next (POST /eth/v1/validator/duties/sync/{epoch}, asked at the period’s first epoch) and posts sync_committee_subscriptions for the current period’s seats, until the period’s end, so the node joins the subnets. The next period’s are added once its boundary is within four epochs. A member sleeps until SYNC_MESSAGE_DUE_BPS (SYNC_MESSAGE_DUE_BPS_GLOAS from gloas), reads /eth/v1/beacon/blocks/head/root, signs it and submits one message per validator. It refuses to sign when the node reports the head optimistic. A member selected by the selection-proof hash for a subnet then waits for CONTRIBUTION_DUE_BPS (CONTRIBUTION_DUE_BPS_GLOAS), fetches the node’s contribution for that subnet and publishes it wrapped and signed. A subnet whose contribution cannot be fetched is skipped without stopping the others. Duties for wall slot S are those of the period containing S + 1, since members assigned to slot S sign for S - 1. Both halves are bounded by the end of the slot.

Voluntary exits are signed by the keymanager API’s voluntary_exit route and by ethlambda voluntary-exit.

Doppelganger protection

Off unless --enable-doppelganger-protection is passed. A doppelganger is a second validator client running the same key, usually a key moved to a new machine while the old one still runs. Slashing protection cannot see it, since each client’s record holds only what that client signed. With the flag on, a key signs no attestation or block until its beacon node has watched it stay silent for a full epoch, through the standard POST /eth/v1/validator/liveness/{epoch}. The rule is Lighthouse’s:

  • A key loaded at startup, or imported through the keymanager API, in epoch E is watched from E + 1. Activity in E is not held against it, since it is most likely this client’s own previous process, restarted within the epoch.
  • Three quarters into every slot the client asks about the previous epoch and the current one. A key found live in an epoch it is watched for stops the client with an error naming the validators.
  • An epoch counts as clean at the last slot of the epoch after it, once its attestations have had their full inclusion window, and only when both questions were answered and the key was explicitly reported not live. A failed query, or a beacon node reporting itself syncing or optimistic, makes no progress. With several --beacon-nodes, a syncing one is skipped for the next.
  • So a key registered in E signs from E + 3, missing two to three epochs of attestations. A key registered in epoch 0 (before genesis or during the chain’s first epoch, at startup or by import) signs at once, as Lighthouse’s do: every validator missing those epochs together could stall a new chain.
  • An epoch that could not be counted clean (no beacon node answered at its deciding slot) is not asked about again, since a node answers only for the previous, current and next epoch: the key waits for the next epoch instead, and the miss is logged at error.

Withheld while a key is checked: attestations, blocks (with the RANDAO reveal) and aggregates, the last because a node marks an aggregator live and would report this client as a doppelganger of itself. Everything else goes on: duties are fetched and subnets subscribed, so the key is ready the moment it is cleared, and sync committee messages and contributions, payload timeliness votes, builder registrations, proposer preferences and voluntary exits are signed as usual, as Lighthouse’s client signs them during its own check. None of them is slashable, and an ethlambda beacon node counts none of them as liveness: it counts attestations, aggregates and block proposers. A beacon node that did count one of them (a sync committee message, say) would report this client’s own message back as a doppelganger and stop it; against such a node, leave the flag off.

A key with no validator index yet is not asked about and stays withheld; with no index it has no duties either. A key deleted through the keymanager API is no longer checked, so a copy the operator now runs elsewhere on purpose does not stop this client, and importing it again starts the check again.

Under a supervisor that restarts the client (Restart=on-failure), a detection becomes a restart loop: each start checks again and stops again for as long as the other client runs. That is safe, since a key under the check signs nothing, but the loop does not end until the other client is found and stopped. The check is not foolproof either: two clients with the same key started together both see silence and both start signing, and a doppelganger that is down for the epochs checked goes unseen until it comes back, when nothing is checking any more. ethlambda_validator_doppelganger_detecting counts the keys still withheld.

Duty offsets come from the network

The slot length and the duty offsets are read from the beacon node’s /eth/v1/config/spec, not divided out of a compiled-in constant. The specification states them as SLOT_DURATION_MS plus basis points of it, ATTESTATION_DUE_BPS and AGGREGATE_DUE_BPS, which on mainnet’s 12-second slot work out at 3999 ms and 8000 ms. Gloas moves both earlier (ATTESTATION_DUE_BPS_GLOAS, AGGREGATE_DUE_BPS_GLOAS) and adds PAYLOAD_ATTESTATION_DUE_BPS (and PAYLOAD_DUE_BPS, which the node uses), so the clock picks the pair by the fork of each slot’s own epoch. The sync committee offsets (SYNC_MESSAGE_DUE_BPS, CONTRIBUTION_DUE_BPS and their _GLOAS variants) are read and picked the same way.

SECONDS_PER_SLOT no longer exists in the specification and is accepted only as a fallback, since deployed nodes still send it. A node sending both is required to agree with itself.

Proposer duties are less durable than attester ones

Worth knowing if a proposal is ever missed after a reorg. An attester schedule depends on the block two epochs back and survives anything shallower; a proposer schedule depends on the block one epoch back, so a reorg that leaves attester duties untouched can still move a proposer between slots. This client fetches proposer duties once per epoch, at the boundary, so a reorg inside the epoch is not picked up until the next one.

Remote signing (Web3Signer)

A validator’s key can stay in a Web3Signer instead of this process. Each signature is then one POST /api/v1/eth2/sign/{pubkey} carrying the message in full (the attestation data, the block header, the aggregate, and so on), the fork it is signed under and the signing root, and the signer answers with the signature. Every duty this client performs signs this way when the key is remote, the gloas envelope and payload attestation included; a slot’s attestations are requested concurrently, so a hundred keys behind one signer cost one round trip rather than a hundred in series.

Because the message travels in full, the signer’s own slashing protection applies to it, on top of this client’s: a remote key has a record in slashing_protection.json like a local one, and a block or attestation is checked against it and recorded before the signer is asked. So a remote key written into the definitions file by hand is refused at startup until it has a record, the same as a local keystore; one imported through the keymanager API is registered as it is imported. The two records are separate (see Spec Deviations): a key moved to or from a signer carries its history through the signer’s own tools. A signer refusal (412) is logged, counted as a signing failure and never retried; so is a key the signer does not hold, a signer that cannot be reached, and an answer that does not verify: every signature a signer returns is checked against the validator’s public key and the signing root before it is used, so a signer holding another key under that pubkey, or computing another root, costs the signature rather than publishing one no peer accepts. That check runs off the duty loop, a core per signature, so a large batch of answers does not hold the loop up. Each duty asks for its signatures all at once and gives each one 2 seconds: a signer that has not answered by then loses the signatures it owes and no others, so the duty publishes whatever arrived, local keys and other signers’ keys included. It publishes them together, though, so while a signer hangs every duty’s batch goes out up to 2 seconds late, the local keys’ share of it too: an attestation is then published 2 seconds after the attestation offset, still ahead of the aggregation one. One signer is sent at most 64 requests at a time and the rest of a batch waits its turn inside the same 2 seconds, so a signer costs this client 64 connections however many keys it holds; the sub-command also raises its open-file limit at startup, as node and beacon do. Aggregator selection proofs are remembered once produced, so the one the epoch’s subnet subscription asked for is not asked for again by the aggregation. Those subscriptions are sent from a task of their own, started once the epoch’s first slot has had its block, so the round trips for their selection proofs never stand between a slot boundary and a proposal. With no duty waiting on that task, its proofs get 8 seconds rather than 2: one that misses is a duty subscribed without the aggregator role, and at startup, or with thousands of remote keys, two epochs of proofs queue for the signer’s 64 request slots. Nothing is asked of the signer at startup or at import: a signer may start after this client does.

A voluntary exit for a remote key is signed the same way (VOLUNTARY_EXIT), through the keymanager API’s voluntary_exit route. The signer derives an exit’s root itself and refuses a request naming another, so it is told the one fork version the exit is signed under, as both previous_version and current_version: from deneb on that is the capella version (EIP-7044), not the fork the schedule has at the exit’s epoch. ethlambda voluntary-exit decrypts a keystore file, so it signs for local keys only.

Builder registrations (VALIDATOR_REGISTRATION, with --builder-proposals) and gloas proposer preferences (PROPOSER_PREFERENCES) are signed by the signer too. A registration is sent with no fork_info: its domain is the genesis fork version under a zero validators root, which the signer takes from its own network configuration. A preference is told the fork at its proposal epoch, the one its domain comes from. Like the subscriptions, the epoch’s full registration send starts after the slot’s block, and each chunk of it gets the same 2-second budget; a registration that fails to sign is left out until the next epoch’s send.

A remote key is declared in validator_definitions.yml with type: web3signer and a url where a local entry has type: local_keystore and its two keystore paths:

- enabled: true
  voting_public_key: "0x9612…0d07"
  type: web3signer
  url: https://signer:9000

or imported at runtime through POST /eth/v1/remotekeys (below). A url left out of that request means --web3signer-url. An entry written without a type (every entry from before remote signing) is read by its fields; one naming both keystore paths and a url is refused at startup rather than read as either. So is a web3signer entry carrying a field this client does not implement, such as Lighthouse’s root_certificate_path: skipping it would sign through a connection the operator did not describe. description is the one exception, since Lighthouse writes it on every entry, and suggested_fee_recipient, graffiti and gas_limit are not such fields: they are read on either kind of entry (see the proposer settings below). A local entry is read past the fields this client does not have, so a file Lighthouse wrote for local keystores loads as it is; those fields are not kept when the file is next rewritten. The url must not carry credentials, a query string or a fragment.

The signer is reached over HTTP or HTTPS. HTTPS is verified against the Mozilla root store bundled into the binary (webpki-roots), not the operating system’s trust store, and no other CA can be added: a signer behind an internal or self-signed CA fails every TLS handshake, and every signature for its keys is then counted as a signing failure. Client certificates are not supported either. Put such a signer behind a certificate from a public CA, or reach it over plain HTTP on a private network.

The keymanager API

Off unless --enable-keymanager is passed. It serves GET, POST and DELETE /eth/v1/keystores, authenticated with a bearer token read from api-token.txt in the validators directory and generated there on first start if absent. The token file is written 0600 and a file too short to be a real token is refused rather than accepted.

It serves GET, POST and DELETE /eth/v1/remotekeys for the keys a Web3Signer holds. The two routes partition the store: /keystores lists and deletes local keys only, /remotekeys remote keys only, and a key asked of the wrong route is not_found. An import of a key either route already holds is duplicate. POST /remotekeys persists each key to the definitions file and registers it in the slashing-protection record before it starts signing, the same order the keystores import uses, and readonly is always false: this client has no key it cannot delete. These routes carry no slashing-protection history, since the specification gives them no field for it: a remote key imported with no record starts as never having signed, and DELETE /remotekeys leaves the record in place. DELETE /keystores exports nothing for a key a remote signer holds.

A delete through either route reads the definitions file once and saves it once for the whole request, and takes the keys out of memory in between, so a request naming hundreds of keys does not hold up the duties’ signatures. The two routes can only disagree with the file about a key’s kind after the file was edited by hand under a running client. A delete that then finds the key in memory as its own kind, and in the file as the other route’s, stops signing with it and answers error naming the other route, not deleted: the entry it leaves would load the key again at the next start. DELETE /remotekeys of a remote entry whose key this process runs from a local keystore removes the entry and leaves the local key, and its per-validator settings, as they are. Its answer is error too, naming /eth/v1/keystores, and never deleted: the key is still signing here until that route removes it.

A deleted key’s fee recipient is no longer sent to the beacon node, from the next slot on. The node keeps the address it was last given for that validator until it expires the entry or restarts, so a client the key moved to on the same node prepares it with its own address without this one overwriting it. An imported key’s fee recipient is first sent at the next epoch boundary, when its index is resolved, which is also when its proposer duties are first fetched.

It also serves POST /eth/v1/validator/{pubkey}/voluntary_exit, which signs a voluntary exit for a validator this client holds, in a local keystore or in a remote signer, and answers with the SignedVoluntaryExit, for the exit’s epoch query parameter or the current epoch when none is given. It does not publish the exit. As the specification has it, the caller hands the message to a beacon node’s POST /eth/v1/beacon/pool/voluntary_exits, or holds on to it. The validator index comes from the beacon node on each call, so a key whose deposit the chain has not processed yet is a 404 saying so.

And it serves GET, POST and DELETE on /eth/v1/validator/{pubkey}/feerecipient, /graffiti and /gas_limit, which give one validator its own value in place of the command line’s default:

A validator imported since the last epoch boundary, or with no index on chain yet, is first sent once an epoch boundary resolves its index. These persist. Each is written onto the validator’s entry in validator_definitions.yml (suggested_fee_recipient, graffiti, gas_limit, Lighthouse’s layout, so a file Lighthouse wrote loads here with the three in effect) before the request is answered, and loaded again at startup, so a restart runs with what the operator set. They are the validator’s settings whichever way its key signs, so a key in a remote signer takes them too, on its web3signer entry. The file does not go back to Lighthouse unchanged: a save here keeps only the fields this client reads, so an entry’s description and builder_* settings are dropped the first time this client rewrites the file, which every one of these requests does.

A write that fails is a 500 that changes nothing. One 500 is different and says so: the file was replaced but its directory could not be flushed, so the change is in effect, here and at the next start, and only its survival of a power loss is in doubt; repeating the request flushes it. A request made while a keystore import is running is answered once the import is done, since both write the same file. Where the file names one key twice, the change goes to the enabled entry, the one a restart reads.

The fields may also be put in the file by hand before the client starts; a malformed one refuses startup, before any keystore is decrypted. Deleting a keystore drops its entry and its values with it. Importing a key whose entry is already in the file, a re-import or one that enables a disabled entry, keeps the entry’s values and runs with them at once; if one of them is malformed the import is refused and nothing is written.

A few answers worth knowing: GET feerecipient is a 500 when the validator has no address and there is no --suggested-fee-recipient default, as Lighthouse answers it; POST feerecipient refuses the zero address, as the specification requires; POST graffiti refuses text over 32 bytes rather than truncating it; POST gas_limit refuses 0, as --gas-limit does; and every route answers 404 for a key this client does not hold.

The keystore routes carry slashing-protection history. POST refuses every key in the request if its slashing_protection does not parse or is for another chain, and otherwise writes that history before any key is saved, so a key never loads ahead of it; a validator the history names without a keystore in the request gets a record too. DELETE returns the deleted keys’ records as a minimal EIP-3076 interchange, answering not_active for a key that is gone but still has a record.

The specification requires TLS. This binds to --http-address, loopback by default; exposing it further means putting a TLS terminator in front.

Metrics

Served on --metrics-port, prefixed ethlambda_validator_ rather than the lean_ used elsewhere in this repository, since this process follows the beacon chain. Every series is registered at startup so it reads zero rather than being absent before its first event, which is what lets an alert fire on “attestations stopped”. See Metrics.

voluntary-exit

ethlambda voluntary-exit signs a voluntary exit for one validator and hands it to a beacon node, which validates it against its head and gossips it. It is a command of its own rather than part of ethlambda validator: it takes one keystore and none of the client’s flags, runs once and ends.

ethlambda voluntary-exit \
  --keystore ~/validators/0xabc.../voting-keystore.json \
  --password-file ~/secrets/0xabc... \
  --beacon-node http://localhost:5052
FlagDefaultMeaning
--keystorerequiredThe validator’s EIP-2335 voting keystore
--password-filerequiredThe file holding that keystore’s password. A trailing newline is ignored
--beacon-nodehttp://localhost:5052Base URL of the beacon node’s HTTP API. One node, not a list: this is a one-shot command, and an operator whose node is down picks another
--epochthe current epochThe exit’s epoch, before which the chain refuses it. An earlier one is as good as the current one. A later one needs --presign: a node refuses an exit whose epoch has not come, so the command refuses to publish one
--presignoffSign the exit and print it as JSON on stdout without publishing it, for an operator who wants to hold a signed exit for later. Logs go to stderr, so the JSON pipes cleanly into a file
--no-confirmationoffPublish without asking for the confirmation phrase. For scripts; use with care
--no-waitoffReturn as soon as the beacon node has accepted the exit, without waiting for the chain to process it

A voluntary exit is irreversible. Once the chain processes it the validator is queued to leave, stops earning after its exit epoch, and the key can never validate again. So before publishing anything the command refuses a beacon node that is still syncing, refuses a validator the chain would refuse (one that is not active_ongoing, or not yet SHARD_COMMITTEE_PERIOD epochs past its activation, naming the epoch it becomes eligible at), and then prints a warning and asks for the phrase Exit my validator on stdin. Anything else, an empty stdin included, aborts without publishing and with a failing exit status, so a script cannot take an exit that never went out for one that did.

The shard committee period is measured the way the chain measures it: against the epoch the exit is processed in, which is now for an exit being published and the exit’s own epoch for a --presign one naming a later epoch. Its length is the beacon node’s own SHARD_COMMITTEE_PERIOD, read from /eth/v1/config/spec, so a devnet that shortens it is followed. One rule of the chain’s cannot be checked up front: from electra on it refuses a validator with a partial withdrawal still pending. That refusal comes back as the beacon node’s 400, with its reason.

After publishing, unless --no-wait is given, it polls the validator’s status once a slot, for up to two epochs. When the chain reports active_exiting it prints the current, exit and withdrawable epochs and how long until the exit epoch, and returns; keep the validator running until that epoch, since it still has duties until then. Any later status (exited_*, withdrawal_*) and active_slashed end the wait too, reported as such. If the chain has not processed the exit when the wait runs out, the command says so and returns successfully, since the exit was published; a beacon node that cannot answer a poll is asked again at the next slot rather than failing the run.

Exits are signed for the fork that processes them, not the one their epoch falls in. From deneb on that is CAPELLA_FORK_VERSION whatever epoch the exit names (EIP-7044), an epoch from before deneb included, so a pre-signed exit stays valid across every fork to come. The command signs that way, and the keymanager API’s voluntary_exit route does too.

slashing-protection

Moves the validator client’s EIP-3076 history in and out of its --validators-dir, offline. It takes the lock the client holds while running, so it refuses while a client runs on that directory, and it needs no beacon node: the record names its own chain.

# Bring a key's history from another client before its first start here.
ethlambda slashing-protection import --validators-dir ./validators interchange.json

# Hand the history over before running the keys elsewhere.
ethlambda slashing-protection export --validators-dir ./validators out.json
ethlambda slashing-protection export --validators-dir ./validators --pubkeys 0xab..,0xcd.. out.json
Sub-commandDoes
import <file>Merges a version 5 interchange, complete or minimal, into the record. Each validator is reduced to its highest slot, source and target and merged by maximum, so nothing already recorded is lowered and slashable data in the file is absorbed rather than refused, except an attestation whose source is at or past its target outside genesis, which is refused. All or nothing. With no record yet, the import creates one for the interchange’s chain, and a failed import creates nothing; the client refuses the record at its next start if that is not its beacon node’s chain
export [--pubkeys ...] <file>Writes the record, or the named validators’ part of it, as a minimal version 5 interchange, readable by its owner only. A named validator with no record fails the export, so a typo or the wrong directory cannot produce a file that reads as complete. Writes nothing to the directory, and the lock is on the directory itself, so a read-only one will do. Refuses to overwrite an existing file
