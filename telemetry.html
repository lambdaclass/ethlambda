ethlambda

Block telemetry (ClickHouse)

With --telemetry.clickhouse-url, a node writes one row per point in each block’s life, and per data column arrival, to a ClickHouse table named block_events. The table layout is Silver’s, so both clients’ rows can share one table and one set of queries.

Rows are batched and sent over ClickHouse’s HTTP interface on a one second tick, with one request in flight at a time, since ClickHouse writes a part per insert. A full request’s worth of backlog goes out without waiting for the next tick. A failed request is retried on a later tick, with the backlog capped so an unreachable ClickHouse costs bounded memory (the oldest rows are dropped first). A batch ClickHouse rejects as malformed (HTTP 400) is dropped instead, since retrying it would block every later row. Refusals are logged at warn on the first and then at most once a minute, with the batches and rows dropped since the last report, so a table whose schema the rows do not fit stays visible. A row field the table lacks is ignored rather than refusing the batch (input_format_skip_unknown_fields), so a table created by an older layout still takes the columns it has.

On a graceful shutdown the writer sends what is still pending before the node exits, waiting at most 12 seconds; rows it cannot deliver are counted as dropped.

Delivery is at least once: a request that times out after ClickHouse committed it is sent again, so a query should take min/any per block, stage and client rather than count rows. Rows still pending when the node exits are lost. lean_telemetry_rows_total and lean_telemetry_insert_failures_total say what happened to the rows. The table is created on first use; that statement is best effort, so a user that may insert but not create still works against an existing table.

Flags

FlagDefaultMeaning
--telemetry.clickhouse-url (or ETHLAMBDA_TELEMETRY_CLICKHOUSE_URL)offClickHouse HTTP endpoint, e.g. http://127.0.0.1:8123. user:pass@ in the URL is sent as basic auth; ?database= passes through. Pass a URL with a password through the environment variable: a command line is readable by any local user
--telemetry.client-name--node-id (node), ethlambda@<hostname> (beacon)meta_client_name on every row; requires the URL

meta_network_name is the network’s CONFIG_NAME on beacon (unknown when a loaded network directory has none) and lean-<genesis time> on node (the genesis Unix time in seconds), so lean devnets sharing one table, or one devnet reset with a new genesis, stay apart.

In a container, set --telemetry.client-name (or the container’s hostname): Docker’s default hostname is the container ID, so the beacon default would change on every recreate and split one node’s rows across names. Only http/https URLs are accepted; ClickHouse’s native port (9000) is not this interface. A rejected URL is never echoed back, since it may hold a password.

Stages

Block rows are written once a block’s import finishes (imported by its own state transition, or failed); a block that never leaves a hold has no rows, and a re-delivery of a block already stored writes none. Silver’s names are used where the meaning matches; every other section of the import timing is written as <section>_start and <section>_end. The only block that writes no rows is lean’s locally built one, which crossed no wire and carries no source. A block re-delivered after waiting for its slot reports under its original source and adds defer_start and defer_end. On beacon, a proposal handed over by a validator client enters as gossip, with received at the hand-off and no decode_end row.

StageMeaning
receivedThe block came off the wire (gossip) or was handed to the chain actor (req/resp)
da_availableThe data-availability check passed for a block that needed columns. A block with nothing to wait for (no blobs, or gloas, whose data gates the envelope instead) writes da_check_end instead
el_sent, el_verdictengine_newPayload sent and answered; only when an execution client answered
stf_doneThe state transition finished
attestableThe new head including the block is computed, as in Silver. Beacon recomputes the head once per arriving block, after the whole import cascade, so every block that cascade imported and the new head includes gets the same time (a block imported onto a losing branch never became attestable and writes none), and only when that head computation succeeded (a failed one moves nothing, so writes no attestable); lean updates its head per block
failedThe import failed; stf_done and lean’s attestable are then written as stf_end and fc_head_end
column_recv, column_validatedA data column arrived, and passed validation. Written only for a column that passed (or, for column_recv, was judged to wait for its block), as Silver does, so rejected columns and re-delivered stored ones write nothing. At least once per block, column and stage: a column delivered again while it waits, or two copies passing at once in separate deliveries, write again, so take the earliest. A copy repeated within one delivery (one peer’s answer, say) is dropped unchecked and writes nothing. A column that waited writes column_validated with source recheck, so join the two on block root and column index, not on source. By-root and by-range answers stamp every column with the moment the whole answer reached the handler. A gossip-accepted column’s column_validated comes after the verdict’s trip back through the p2p actor; a checked one’s when its check finished, which is when the KZG sub-batch it was verified in (at most 16 of its block’s columns) finished, not when its block’s last one did
cascade_*, prune_*, get_head_*, fcu_*Once per arrival, filed under the arriving block, when that block was imported in that cascade

With an execution client, ethlambda computes the block’s state transition while engine_newPayload is in flight, and keeps it only for a verdict that agrees with it. el_sent to stf_done still covers both, but stf_start no longer separates them. When the overlapped transition is kept, it ran inside el_sent..el_verdict, and stf_start..stf_done is only the rest of on_block after the verdict. When it is discarded (an Invalid verdict), stf_start..stf_done runs the transition again. The overlapped transition writes no row of its own: the import’s log line and lean_block_import_phase_seconds{phase="stf"} count it.

source and verdict are ethlambda’s own values on every row, not Silver’s (Gossip, Rpc, Syncing, …); a query shared with Silver’s rows must match both.

Only the stages a block actually crossed are written. decode and queue write only their _end rows, since received is their start. admit_* is the chain actor’s admission section; it is written here and listed in no other doc.

Known gaps

  • On a node with a validator client, its own beacon proposals appear under source = 'gossip' with near-zero arrival latency. Filter them out by their missing decode_end row when comparing with another client.

  • A held block keeps its arrival marks (received, decode_end, queue_end, defer_*, admit_*, the starts of its waits) across the hold, but the sections after them (guards_*, da_check_*, the import itself) are the final pass’s: an earlier pass’s failed check is not written.

  • A block re-delivered while held reports the last delivery as received, not the first (the import timing histogram does the same).

  • Some blocks released from a hold carry no timings and write no rows, e.g. one held again by the execution client after its columns arrived. A block the execution client could not judge, or that is not an optimistic candidate, writes no rows either.

  • An ancestor read back from storage (mainly after a restart) reports that read as its received.

  • On gloas the payload goes to the execution client with its envelope, not the block, so gloas blocks have no el_* rows; a gloas block held for its parent’s payload has no wait section of its own.

  • Lean’s attestable is the end of its head update plus the bookkeeping an import ends with (events, eviction, table sizes), sub-millisecond in practice.

A query to start from

Per-block arrival to attestable, in milliseconds:

SELECT block_root, any(slot) AS slot,
       (toUnixTimestamp64Nano(minIf(event_date_time, stage = 'attestable'))
      - toUnixTimestamp64Nano(minIf(event_date_time, stage = 'received'))) / 1e6 AS total_ms
FROM block_events
WHERE meta_client_name = 'ethlambda@<host>' AND event_date_time > now() - INTERVAL 1 HOUR
GROUP BY block_root
HAVING countIf(stage = 'attestable') > 0
ORDER BY slot DESC
LIMIT 50

Retention

The table has no TTL. Set one as an operator, e.g. ALTER TABLE block_events MODIFY TTL toDateTime(event_date_time) + INTERVAL 14 DAY.
